# Mirrors PC-8801 MC 한글 패치 설계 및 작업 기록

이 문서는 영문 패치를 기반으로 진행하는 한글화의 확정 방향, 시험 구현, 실패 원인과 남은 검증 항목을 기록한다. 영문 패치 자체의 구조는 `docs/english-source-structure-map.md`, 원본 CD의 물리·논리 구조는 `docs/original-cd-image-analysis.md`를 기준으로 한다.

에뮬레이터는 사용자의 명시적인 지시가 있기 전에는 실행하지 않는다. 이 문서에서 별도 표시가 없는 확인 결과는 소스·바이너리·주소표를 이용한 정적 분석 결과다.

## 1. 기준과 작업 원칙

- 완성·검증된 영문 패치의 CD 배치와 출력 경로를 기준으로 한다.
- 기존 ASM과 VWF 화면 합성 코드를 최대한 유지한다.
- 영문 패치 분석·기준 구현은 `reference/mirrors_tools/Ruby/`를 사용한다. 한글 패치의 실제 빌드·수정은 `korean_mirrors_tools/python_tools/`의 Python 구현으로 수행한다. Python은 Ruby 2.7.4 x64(`chunky_png` 1.4.0, `-EUTF-8`) 영문 빌드 결과와 바이트 단위 호환을 확인한 상태다.
- 원본 CD 이미지와 추출 플로피는 Git에 넣지 않는다.
- 영문 패치의 44개 2D 입력, 16개 2HD 그룹과 서브디스크 배치를 유지한다.
- CDDA 트랙은 수정하지 않고 Track 2 데이터만 재구성한다.
- 시험 파일과 생성 이미지는 저장소의 ignore 대상인 `Temp` 작업 영역에 둔다.

## 2. 확정된 문자 사양

### 2.1 글리프

- 한글 글리프는 8×16 픽셀, 1비트 형식이다.
- 글리프 하나는 16바이트다.
- 첫 시험 목표는 500자짜리 하나의 연속 글리프 표다.
- 500자 글리프의 총 크기는 `500 × 16 = 8000 = 0x1F40`바이트다.
- 실제 번역에서 필요한 고유 글자 수는 번역문을 집계한 뒤 확정한다. 500자는 시험 규격이다.

### 2.2 2바이트 토큰

- 500자 이상을 1바이트 코드로 표현할 수 없으므로 한글은 2바이트 토큰을 사용한다.
- 현재 시험 규격은 제어 바이트와 충돌하지 않는 500개 값이다.
- 상위 바이트는 `0xE0`, `0xE1`, `0xE2`를 사용한다.
- 하위 바이트는 `0x40~0x7E`, `0x80~0xFC`만 사용한다. 따라서 `0x00~0x1F`, `0x22`, `0x7F`, `0xFF`를 토큰 내부에 넣지 않는다.
- 토큰 범위는 `E040~E0FC` 188개, `E140~E1FC` 188개, `E240~E2BC` 124개로 총 500개다.
- 문자열에는 상위 바이트, 하위 바이트 순서로 저장한다.
- 글리프 인덱스는 상위 바이트별 188칸을 기준으로 계산한다. 하위 바이트가 `0x40~0x7E`이면 `low - 0x40`, `0x80~0xFC`이면 `low - 0x41`을 해당 뱅크의 인덱스로 사용한다.
- VWF는 ASCII·기존 제어 바이트는 기존처럼 처리하고, 상위 바이트가 `E0/E1/E2`일 때만 다음 바이트를 한글 토큰의 일부로 소비한다.
- ASCII 병용, 제어 토큰, 문자열 종료 규칙은 아직 최종 확정하지 않았다.

### 2.3 문자열 크기

- 한글 한 글자는 문자열에서 2바이트를 차지하므로 같은 글자 수의 영문 문자열보다 BASIC 데이터가 커질 수 있다.
- 모든 시나리오가 동시에 RAM에 상주하는 것은 아니며 현재 `CMD RUN`으로 실행 중인 BASIC 하나가 대상이다.
- 각 시나리오의 컴파일 결과는 활성 Python 빌드 도구의 `0x3000`바이트 경고·안전 목표를 기준으로 개별 검사한다. 이 값은 원본이 반드시 지켜야 했던 확인된 절대 RAM 상한은 아니다. 한글판은 재패킹과 검증의 기준으로 각 생성 파일을 `0x3000` 이하로 유지한다.
- 시나리오 출력 루틴이 `MID$(BM$,K1,1)`처럼 한 바이트씩 자르는 구간은 한글 토큰을 둘로 분리하므로 2바이트 단위 순회로 수정해야 한다.
- 메뉴처럼 문자열 전체를 `CMD KANJI`에 넘기는 경로는 VWF 내부가 2바이트 토큰을 처리하면 호출 형식을 유지할 수 있다.
- 영문 기준 Ruby `BasicCompiler.rb`의 줄 길이 계산은 `@widthData[l.ord - 0x20]`처럼 ASCII 값을 직접 인덱스로 사용한다. 한글판 활성 Python `basic_compiler.py`에서는 길이·줄바꿈 계산을 한글 토큰 ID 기준으로 교체해야 한다.

### 2.4 원본 Track 2 초반 문자열 실측

원본 intro/menu의 실측 문자열 표와 Track 2 추출 근거는 [문자열 바이트 용량 재계산](string-byte-capacity-analysis.md)에만 유지한다. 그 실측 결과는 전각 숫자·공백·부호를 포함한 화면 표시 문자열이 문자 수 × 2바이트로 저장됨을 확인한다. 반면 menu의 `n/N/y/Y`는 화면 출력이 아닌 `INKEY$` 키보드 ASCII 비교값이므로 1바이트다.

따라서 한글 용량 계산에서도 화면에 표시되어 `CMD KANJI`로 전달되는 문자열과 키 입력·분기 판정용 BASIC 문자열을 구분한다.

### 2.5 영문 저장 루틴 안내문의 한글화

영문 Ruby 소스 분석 결과, `stringsImport.csv`에는 번역란이 비어 있는 저장 관련 원문 행이 300개 있다. 이 중 299행은 100개 `allowSave=true` 스크립트의 원래 BASIC 저장 안내문이고, 나머지 1행은 `disk30/NO62/9565`에 남은 대조표 중복 항목이다.

영문 패치의 `DataImporter#basic_applySavePatch()`는 문자열 CSV를 처리한 뒤가 아니라 BASIC 컴파일 전에 저장 루틴을 직접 교체한다.

- BASIC `10000`: `Save game? (press Y or N)`으로 교체
- BASIC `10040`: `Select slot (1-9, ESC to exit):`으로 교체
- BASIC `10049~10080`: 키 입력·슬롯 저장 루틴으로 교체
- BASIC `10090`: `Done. Press ENTER to continue.`를 추가
- BASIC `10110~10150`: 원래 SAVE 디스크 재삽입 루틴을 제거

따라서 원문 299행은 `stringsImport.csv`의 번역문으로 직접 처리되는 문자열이 아니다. 최종 영문 이미지에는 저장 패치 코드가 삽입한 영문 안내문이 들어가며, 이 안내문은 `GOSUB 5000` 또는 `GOSUB 5100`을 통해 VWF 출력 경로를 사용한다. `NO62/9565` 1행은 실제 BASIC 소스에 문자열이 없어 빌드 결과에 영향을 주지 않는다.

한글판에서 저장 안내문까지 한글화하려면 299행을 개별 번역하는 것이 아니라, 활성 Python `data_importer.py`의 `basic_applySavePatch()`에 있는 `10000`, `10040`, `10090`의 하드코딩 문구를 한글 2바이트 토큰 문자열로 수정해야 한다. 이 추가 안내문은 영문 번역 데이터 4,982행에 포함되지 않는 별도 소스 문자열이다.

#### 2.5.1 빌드 소스의 하드코딩 출력 문자열

활성 Python `data_importer.py`가 CSV에서 읽지 않고 BASIC 패치 라인에 직접 삽입하는 출력 문자열은 총 7개다. 이 항목은 영문 Ruby `DataImporter.rb`와 동일한 빌드 규칙을 유지한다.

| 구분 | 영문 문자열 | 삽입 위치·경로 |
|---|---|---|
| 오프닝 | `This story is a work of fiction.` | 오프닝 VWF 패치 |
| 출력 마커 | `>>>` | 공통 VWF 출력 패치 |
| 저장 | `Save game? (press Y or N)` | `basic_applySavePatch()` 10000행 |
| 저장 | `Select slot (1-9, ESC to exit):` | `basic_applySavePatch()` 10040행 |
| 저장 | `Done. Press ENTER to continue.` | `basic_applySavePatch()` 10090행 |
| CD 전환 | `Press any key to start reading data from CD-ROM.` | `basic_applyCDswitchPatch()` |
| CD 전환 | `Reading data...` | `basic_applyCDswitchPatch()` |

`>>>`는 언어 문장이 아닌 출력 마커이므로 한글 번역 대상에서 제외한다. 실제로 한글화해야 하는 하드코딩 문장은 나머지 **6개**다.

이 문자열들은 별도 텍스트 파일이나 폰트 파일로 저장되지 않는다. 빌드 과정에서 다음 순서로 해당 BASIC 파일에 포함된다.

```text
Python data_importer.py의 하드코딩 문자열
→ BASIC 패치 라인에 삽입
→ Python basic_compiler.py가 토큰화·인코딩
→ 컴파일된 BASIC 파일의 바이너리에 저장
```

따라서 한글 문자열로 교체하면 문자열이 삽입되는 각 BASIC 파일의 크기가 증가하며, 최종 본문 크기는 해당 파일의 `0x3000` 기준에 포함된다. 저장 문자열 3개는 `allowSave=true`인 여러 스크립트에 반복 삽입되고, CD 전환 문자열 2개도 해당 전환 루틴이 들어가는 스크립트마다 삽입된다. 오프닝 문자열은 오프닝 스크립트에만 들어간다.

`Y/N`, 숫자 슬롯, `ESC`, `ENTER`처럼 키 입력 비교에 사용되는 값은 화면 표시 문자열과 별개이므로 기존 ASCII 비교 규칙을 유지한다. 한글판에서는 화면에 표시되는 6개 문장만 한글 2바이트 토큰으로 바꾸고, 컴파일 후 각 BASIC 파일의 최종 크기·줄바꿈·VWF 출력 폭을 개별 확인한다.

### 2.6 BASIC 스크립트 분할과 Track 2 배치

영문 패치의 `e_scripts.csv`에는 105개의 논리 BASIC 스크립트가 있다. 이 중 현재 `splitPoints`가 지정된 것은 7개이며, 각 스크립트를 본체와 보조 파일의 2개로 나눈다. 따라서 분할 대상 7개는 전체 스크립트 수가 아니라, 2분할이 적용된 스크립트의 수다. 현재 빌드 결과는 논리 스크립트 105개에 보조 파일 7개가 더해진 구조다.

현재 분할 형식은 한 스크립트를 여러 조각으로 쪼개는 형식이 아니라, 한 번에 정확히 두 파일을 만드는 형식이다.

- 본체에는 첫 구간과 마지막 구간을 넣는다.
- 보조 파일에는 가운데 구간을 넣는다.
- 본체의 분기 지점에 `CMD RUN "보조 파일명"`을 삽입한다.
- 본체와 보조 파일은 각각 별도의 BASIC 파일·디렉터리 항목·섹터 할당을 가진다.

따라서 한글화 후 용량이 큰 스크립트가 추가로 발견되면 7개를 고정할 필요는 없다. 2분할 대상에 3개를 더 지정하면 10개, 5개를 더 지정하면 12개가 된다. 이 경우 한 스크립트를 8개나 9개로 나누는 것이 아니라, 2분할을 적용하는 스크립트의 수를 10개 또는 12개로 늘리는 것이다. 한글판 활성 Python 컴파일러는 영문 Ruby의 현재 2분할 방식과 2HD 매핑을 그대로 유지해 적용한다.

추가 분할 대상은 다음 조건을 만족해야 한다.

1. 각 결과 BASIC 본문이 `0x3000`바이트 이하일 것.
2. 분할 지점이 실행 흐름상 안전한 BASIC 줄 경계일 것.
3. 추가로 생성되는 보조 파일이 원래 스크립트가 속한 논리 디스크의 디렉터리·섹터 맵에 들어갈 것.
4. 본체에서 보조 파일로 넘어가는 `CMD RUN` 연결과 파일명이 일치할 것.

현재 영문 패치는 Track 2 전체를 하나의 공유 파일 영역으로 사용하지 않고, 2D 이미지 3개를 2HD 그룹 하나로 패킹한다. 그러므로 추가 보조 파일은 원래 스크립트가 속한 2D 이미지의 파일 디렉터리 엔트리와 섹터 맵 여유를 사용한다. 기존 `i_disks.csv`의 2HD 그룹·서브디스크 매핑은 이미 확인되어 있으므로, 추가 분할만으로 그룹 주소나 menu BASIC의 디스크 선택표를 변경할 필요는 없다.

대상 2D 이미지에 엔트리·섹터가 부족한 경우에만 빈 중복 슬롯을 재활용하거나 다른 서브디스크로 재배치하고, 그때 `e_cddata.csv`, `i_disks.csv`, Track 2 패킹 주소 및 `COMMON COPY` 주소를 함께 갱신한다. Track 2의 물리 여유·원본 중복 슬롯·0 채움 영역의 정확한 수치는 [원본 CD 이미지 분석](original-cd-image-analysis.md)과 [영문 패치 소스 구조 맵](english-source-structure-map.md)에만 기록한다. 즉 7개에서 10개·12개로 늘리는 것 자체는 용량상 문제가 아니며, 실제 한글 번역본을 컴파일할 때 대상 디스크별 파일 크기와 디렉터리·섹터 맵을 다시 계산하면 된다.

## 3. 확장 RAM의 한글 글리프 배치

영문판은 확장 RAM의 32KB CPU 매핑 창(`0x0000~0x7FFF`) 중 앞의 16KB만 다음처럼 사용한다. `E2`는 확장 RAM 접근 제어값이고 `E3`가 선택 뱅크다. 영문 소스는 `E2=0x11`, `E3=0`만 사용한다. 주소와 기종 사양은 [PC-8801 Memory map](https://www.hitchhikr.net/PC-8801%20Memorandum/PC-8801%20Memory%20map.html) 및 [NEC 공식 PC-8801 사양 페이지](https://support.nec-lavie.jp/support/product/data/spec/cpu/b034-1.html)를 참조한다.

```text
0x0000~0x0FFF : VWF 코드
0x1000~0x1FFF : 영문 스크립트 폰트 뱅크
0x2000~0x2FFF : 영문 UI 폰트 뱅크
0x3000~0x3FFF : 영문 메뉴 폰트 뱅크
0x4000~0x7FFF : 영문 패치에서 사용하지 않는 확장 RAM 영역
```

한글 시험판의 500자 표는 기존 폰트 영역 앞에서부터 연속 배치한다.

```text
0x0000~0x0FFF : 기존 구조를 유지한 VWF 코드
0x1000~0x2F3F : 한글 500자 글리프 (0x1F40 bytes)
0x2F40~0x2FFF : 남는 공간 (0x00C0 bytes)
0x3000~0x3FFF : 기존 메뉴 폰트 영역 또는 후속 설계 영역
```

CD Track 2의 `0x10000` VWF와 `0x11000~0x12F3F` 글리프 대응은 500자 시험판 기준이다. 최종 뱅크 1용 VWF·글리프 배치는 별도의 CD 데이터 영역으로 다시 정한다.

중요: 여기서 폰트 영역 `0x3000`바이트는 **전체 수용량**이다. 첫 번째 `copyFnt`의 복사량이 아니다.

### 3.1 글리프 수별 용량

8×16 1비트 글리프와 글리프당 1바이트 폭 값을 기준으로 계산하면 다음과 같다.

| 글리프 수 | 글리프 데이터 | 폭 값 포함 |
|---:|---:|---:|
| 288자 | `0x1200` | `0x1320` (4,896바이트) |
| 500자 | `0x1F40` | `0x2134` (8,500바이트) |
| 600자 | `0x2580` | `0x27D8` (10,200바이트) |

600자의 글리프와 폭 값을 모두 연속 배치해도 기존 폰트 영역 `0x3000`바이트 안에 들어간다. 현재 시험판은 500자 글리프 `0x1F40`바이트를 사용하지만, 실제 시험에서 조건부 2바이트 토큰과 500자 상주·메뉴 출력까지 확인했다. 남은 확장 RAM `0x4000~0x7FFF`는 토큰표·주소표·문자열 오버플로 데이터에 사용할 수 있다.

### 3.2 기존 3뱅크와 현재 500자 표의 관계

영문판의 세 뱅크는 각각 96슬롯이며 `vFontNumber`가 스크립트·UI·메뉴 뱅크를 선택한다. 세 뱅크의 합계 288슬롯은 하나의 288자 토큰표가 아니라 같은 ASCII 슬롯을 용도별로 재사용하는 구조다.

초기 500자 시험은 `0x1000~0x2F3F`의 하나의 연속 글리프 표를 2바이트 토큰으로 직접 지정하는 방식이었다. 따라서 시험판에서는 기존 `vFontNumber << 12` 주소 계산을 그대로 사용하지 않고, 한글 토큰에 대해 `0x1000 + index × 16`을 계산했다. 이 방식은 500자 출력 시험용이며, 최종 한글판의 영문·한글 뱅크 분리 방향과는 구분한다.

### 3.3 현재 확정 방향: 영문·한글 뱅크 분리

영문 폰트와 한글 폰트를 하나의 글리프 표로 합치지 않고, 물리 확장 RAM 뱅크를 나누어 각각의 VWF와 글리프 영역을 유지한다. 이번 출력 수정은 이 배치를 변경하지 않는다.

```text
물리 뱅크 0 (E3=0)
  ├─ 기존 영문 VWF
  ├─ 영문 시나리오 폰트 1
  ├─ 영문 UI 폰트 2
  └─ 영문 메뉴 폰트 3

물리 뱅크 1 (E3=1)
  ├─ 한글용 VWF
  ├─ 한글용 글리프 버퍼
  └─ 한글 1,093자 글리프
```

- ASCII 1바이트는 물리 뱅크 0의 기존 영문 출력 경로를 사용한다.
- 한글 2바이트 토큰은 토큰 분기 후 물리 뱅크 1의 한글 VWF로 전환한다.
- 한글 VWF는 뱅크 1 안에서 글리프 16바이트를 자체 버퍼에 저장한 뒤 기존 VWF와 같은 방식으로 화면 버퍼에 합성·출력한다.
- 한글 글리프를 뱅크 0의 `vKanjiBuffer`로 복사하는 방식은 현재 방향이 아니다. 뱅크별 VWF와 버퍼를 각각 유지한다.
- 뱅크 전환 뒤에도 같은 다음 명령을 실행할 수 있도록 수정 VWF 전체를 두 물리 뱅크의 동일 주소 `0x0000`에 배치한다. 한글 경로가 `E3=1`로 바뀐 뒤 뱅크 1의 동일 VWF에서 계속 실행하고, `_prepareNext`의 동일 주소에서 `E3=0`으로 복귀한다.

한글 글리프 데이터는 `1,093 × 16 = 0x4450`바이트다. 영문 3개 폰트 세트는 물리 뱅크 0에 그대로 유지하고, 한글 뱅크는 VWF와 한글 글리프를 별도로 사용한다. 영문 폰트 영역을 한글 글리프로 덮어쓰지 않는다.

문자 토큰표는 다음처럼 분리한다.

- PC의 CSV 토큰표: 번역문을 2바이트 토큰으로 변환하는 빌드 입력 자료
- 디스크의 BASIC 파일: 변환된 2바이트 토큰이 저장되는 실행 자료
- 실행 중 RAM: 토큰을 순차 인덱스 `0~1092`로 해석하고 `한글 글리프 시작 주소 + index × 0x10`을 계산한다. 토큰 범위가 순차적이면 별도의 대형 조회표를 RAM에 적재하지 않는다.

생산판 토큰은 상위 바이트 `E0~E5`와 안전한 하위 바이트 `40~7E`, `80~FC`를 사용한다. 그룹당 188개이며, 번역문에서 확인한 1,093개 음절을 글리프 인덱스 `0~1092`에 가나다순으로 대응한다. 범위는 `E040~E5D9`이고 `7F` 및 문자열 제어 바이트는 하위 바이트로 사용하지 않는다.

### 3.4 확정 방향: 기존 글리프 배치 유지, 전체 출력 기준 수정

영문 3개 글리프 영역과 한글 뱅크를 하나로 합치지 않는다. 기존 뱅크 배치와 글리프 데이터는 그대로 두고, 본문에서 글리프를 화면에 복사·출력하는 전체 기준만 수정한다.

- ASCII·숫자·부호는 기존 영문 글리프 영역을 계속 사용한다.
- 한글 2바이트 토큰은 기존 뱅크 1 한글 글리프 영역을 계속 사용한다.
- 문자 종류에 따라 서로 다른 세로 보정값을 넣지 않고, 본문 전체의 시작 기준점과 16행 출력 프로필을 조정한다.
- `copyCharToBuffer`, `copyToBuffer`, `printBuffer`의 합성·비트 시프트 방식은 유지한다.
- 메인 메뉴·선택 화면의 기존 11행 경로는 유지한다. 다만 UI 설명·로딩 문구처럼 한글 16행 글리프를 두 줄 이상 출력하는 경로는 별도로 16행 간격을 조정해야 한다.

영문·한글 글리프의 실제 상하 여백 차이는 출력 영역을 조정할 때 참고한다. 글리프 PNG와 뱅크 배치를 다시 합치거나 덮어쓰지 않는다.

### 3.5 본문 전체 출력 기준 수정

본문 전체에 공통 기준을 적용하며, 한글만 별도 위치로 보내지 않는다.

1. `korean_mirrors_tools/python_tools/data_importer.py`의 `basic_applyVWFHandler()`에서 본문 시작 주소를 전체 문자에 공통으로 적용되는 기준점으로 조정한다.
2. 같은 함수의 수동 줄 이동 `BN=BN+&H50*14`는 16행 글리프 출력과 맞지 않으므로 `BN=BN+&H50*16`으로 변경한다. `&H50`은 기존 BASIC 화면 주소 행 간격을 그대로 사용한다.
3. `vwf.asm`의 `copyToBuffer`가 16행을 복사하고 `printBuffer`가 `vpatch1`을 통해 16행을 출력하는 구조는 유지한다. 출력 루프를 한글 전용 루프로 교체하지 않는다.
4. `asmbasic.asm`의 `L9785` 16행 프로필 선택과 `vpatch1=0x11`은 유지한다. 11행 프로필 `L9781`로 되돌리지 않는다.
5. 본문 대화창의 배경·삭제 영역은 16행 출력 범위를 포함하도록 조정한다. 메인 메뉴·선택 화면의 기존 11행 레이아웃은 유지하되, UI 설명·로딩 문구의 다중 행 위치와 창 높이는 별도로 조정한다.
6. `_nextLine`의 `vLineBreakHeight`는 기존 VWF 프로필의 VRAM 단위와 본문 16행 이동이 일치하는지 정적으로 확인한다. 임의의 문자별 Y 오프셋은 추가하지 않는다.

따라서 다음 수정은 하지 않는다.

- `vwf.asm`의 문자별 한글 전용 Y 오프셋 분기
- 영문 출력에는 기존 위치, 한글 출력에는 별도 위치를 적용하는 혼합 기준
- 영문 글리프를 한글 글리프 위에 단순히 덮어쓰는 방식

### 3.6 본문과 UI의 세로 출력 기준 차이

최근 `UI3.PNG` 런타임 화면에서 위·아래 줄이 약 5행 겹치는 현상을 확인했다. 원인은 글리프 PNG가 아니라 UI 경로의 세로 간격이다.

- 본문 경로는 `CMD WIDTH BN,&H60,7`로 `asmbasic.asm`의 `L9785` 16행 프로필을 선택한다.
- 본문 VWF는 `printBuffer`에서 16행을 복사·출력하고, BASIC 줄 이동도 `BN=BN+&H50*16`을 사용한다. 따라서 본문 상단이 잘리지 않고 영문·한글 모두 같은 세로 기준을 사용한다.
- UI 항목 경로는 `CMD WIDTH BN,&H40,7`, `&H50*11`, `CN*11`을 사용하는 영문 11행 기준이다.
- 한글 글리프는 16행을 모두 사용하므로 UI에서 다음 줄이 11행 뒤에 시작하면 약 5행이 겹친다.

따라서 본문과 UI를 같은 방식으로 바꾸지 않는다. 본문은 현재 16행 기준을 유지하고, UI 설명·로딩 문구만 16행 프로필·줄 간격·창 높이에 맞춰 별도로 조정한다. 메인 메뉴와 선택 화면에서 이미 확인된 11행 레이아웃은 그대로 둔다.

## 4. 로더는 기존 두 번의 `0x2000` 복사를 유지한다

영문판 초기 BASIC과 `asmbasic.asm`은 같은 CPU RAM 임시 버퍼를 두 번 사용한다.

| 순서 | CD Track 2 | CPU RAM 임시 버퍼 | 확장 RAM 목적지 |
|---:|---|---|---|
| 1 | `0x10000~0x11FFF` | `0xA300~0xC2FF` | `0x0000~0x1FFF` |
| 2 | `0x12000~0x13FFF` | `0xA300~0xC2FF` | `0x2000~0x3FFF` |

500자 글리프는 이 경계를 가로지르지만 추가 로드는 필요 없다.

- 첫 번째 복사: 글리프 `0x1000~0x1FFF`
- 두 번째 복사: 글리프 `0x2000~0x2F3F`

따라서 로더의 올바른 기준은 다음과 같다.

```text
copyFnt BC = 0x2000
intro.bas 첫 로드 = COMMON R,13382,&HA300,&H4
intro.bas 둘째 로드 = COMMON R,13386,&HA300,&H4
둘째 copyFnt 목적지 = 0x2000
```

위 두 번의 복사는 영문 패치의 물리 뱅크 0 로딩 기준이며 그대로 유지한다. 한글판에는 `E3=1`을 선택해 수정 VWF와 한글 글리프를 뱅크 1에 적재한 뒤 `E3=0`으로 복귀하는 별도 로더를 추가했다. 기존 영문 뱅크 0의 두 번 복사와 폰트 3종 배치는 변경하지 않는다.

구현된 물리 뱅크 1 로드는 기존과 같은 `0x2000` 단위 세 번의 복사를 사용한다.

| 순서 | CD Track 2 | 절대 CD 섹터 | CPU RAM 임시 버퍼 | 뱅크 1 목적지 |
|---:|---|---:|---|---|
| 1 | `0x14000~0x15FFF` | `13390` | `0xA300~0xC2FF` | `0x0000~0x1FFF` |
| 2 | `0x16000~0x17FFF` | `13394` | `0xA300~0xC2FF` | `0x2000~0x3FFF` |
| 3 | `0x18000~0x19FFF` | `13398` | `0xA300~0xC2FF` | `0x4000~0x5FFF` |

뱅크 1의 `0x0000~0x0FFF`에는 수정 VWF를 뱅크 0과 동일한 바이트로 복제하고, `0x1000~0x5FFF`에는 1,280슬롯 한글 글리프 RAW `0x5000`바이트를 둔다. 실제 사용 글리프는 1,093개(`0x4450`바이트)이고 나머지 187슬롯은 예약 공백이다. `asmbasic.asm`의 새 로더는 CPU RAM `0x9900~0x9922`에 있으며 기존 `patch_copy` 시작 주소 `0x9980`을 침범하지 않는다.

## 5. 초기 `0x3000` 로더 가설의 정정

초기 시험에서 다음 범위 계산을 한 번에 CPU RAM으로 읽는 로더 복사량으로 잘못 적용했다.

```text
VWF 0x1000 + 500자 글리프 0x1F40 = 0x2F40
0x1000 경계 올림 = 0x3000
```

이 값은 VWF와 글리프가 차지하는 총 범위일 뿐, 한 번에 CPU RAM으로 읽어야 할 크기가 아니다. 또한 초기 `intro.bas`와 `asmbasic.asm`의 `&H6`·`0x3000` 변경은 잘못된 Python 시험 구현에서 나온 값이므로 원본 엔진의 확정 사실로 취급하지 않는다.

초기 잘못된 시험판에는 다음 변경이 들어갔다.

- `intro.bas`: 첫 로드 `&H4 → &H6`
- `intro.bas`: 두 번째 `0x2000` 로드 제거
- `asmbasic.asm`: `copyFnt`의 `BC 0x2000 → 0x3000`

`&H6`은 6개 2048바이트 섹터를 읽는 값이다. 이 변경은 기존 로더 경계를 바꾸므로 현재 설계에서 사용하지 않는다. 한글 500자 시험은 영문판의 두 번의 `0x2000` 복사와 `COMMON R ...,&H4` 로드를 그대로 유지하고, 각 로드 구간에 글리프 데이터를 나누어 배치한다.

따라서 `0x3000` 초과 경고를 이유로 로더를 확장하는 것은 현재 시험의 요구사항이 아니다. 이 정정은 소스·바이너리 대조와 메뉴 런타임 확인 결과에 반영됐다.

## 6. VWF 수정 범위

유지해야 하는 영문판 경로:

- `CMD WIDTH`가 설정하는 출력 위치·문자 수·화면 모드 상태
- `CMD KANJI`에서 확장 RAM의 VWF 진입점 `0x0000`을 호출하는 연결
- `copyCharToBuffer`, `copyToBuffer`, `printBuffer`, `clearBuffers`
- 화면 버퍼 비트 시프트와 VRAM 포트 처리
- `0xB400~0xB41F` 상태 변수

한글판에서 수정해야 하는 부분:

1. 문자열에서 2바이트 토큰 하나를 읽는 부분
2. 생산 토큰 `E040~E5D9`를 인덱스 `0~1092`로 변환하는 부분
3. `0x1000 + index × 16`으로 글리프 주소를 계산하는 부분
4. 2바이트 소비에 맞춘 문자열 남은 길이 처리
5. 8픽셀 고정 폭에 맞춘 여백·다음 글자 위치 처리
6. BASIC 컴파일러와 시나리오 출력 루틴의 2바이트 문자열 처리
7. 기존 영문·한글 글리프의 전체 출력 기준점·상하 표시 범위 정렬
8. 본문 VWF의 16행 출력 프로필과 16행 줄 이동 기준
9. 본문 대화창의 배경·삭제 영역을 16행 출력 범위에 맞추는 처리

`CMD WIDTH`는 글리프 자체의 폭을 지정하는 명령이 아니므로 호출 형식은 유지한다. 기존 VWF의 화면 합성부를 통째로 단순 출력기로 교체하지 않는다.

현재 `vwf.asm`은 영문판의 합성·출력 경로를 유지하면서 `E0~E5` 토큰일 때만 두 번째 바이트를 소비한다. 한글 글리프 주소는 `0x1000 + index × 16`으로 계산하고, `vRightMargin = 5`를 사용해 기존 렌더러의 추가 3픽셀과 합쳐 8픽셀 고정 폭으로 진행한다. ASCII는 기존 영문 글리프 영역과 폭 표를 사용하고, 한글만 뱅크 1의 한글 글리프 주소로 전환한다. 이번 수정은 글리프 표를 통합하는 것이 아니라 본문 전체의 시작 기준점·16행 출력·줄 간격을 맞추는 것이다.

## 7. 현재 시험 자산과 상태

- 임시 500자 글리프 PNG와 RAW가 생성돼 있다.
- 시험 문자표는 제어 바이트를 피하는 `E040~E0FC`, `E140~E1FC`, `E240~E2BC` 500개 토큰을 사용한다.
- 안전 토큰표는 500행·중복 없음·금지 바이트 없음으로 정적 검증했다. 글리프 인덱스와 토큰 인덱스는 1:1로 대응한다.

- VWF만 교체한 `Mirrors_VwfOnly.ccd`도 사용자가 메뉴까지 진입하는 것을 확인했다. 이 결과는 VWF 교체가 초기 실행 경로를 막지 않는다는 뜻이지, 영문 문자열이 한글 2바이트 토큰으로 정상 출력된다는 뜻은 아니다. 영문 메뉴 문자열은 한글 토큰 범위에 들어오지 않으므로 VWF의 잘못된 토큰 대체 경로를 통과할 수 있다.
- 한글 메뉴와 영문 VWF를 조합한 `Mirrors_IntroMenu.ccd`는 출력 규칙이 맞지 않는 부적합한 격리 시험이다.
- 초기 `E000` 계열 토큰 시험은 제어 바이트 충돌 가능성이 있는 설계였으므로 폐기하고 안전 토큰표로 교체했다.
- 기존 영문 VWF 합성 경로를 유지한 상태에서 한글 토큰 읽기와 500자 연속 글리프 주소 계산을 적용했다. VWF 원시 결과는 기존 슬롯 `0x1000` 안에 들어간다.
- 이후 원인 분리를 위해 영문 Ruby 컴파일러와 Python 컴파일러의 결과를 대조한 결과, 두 가지 바이트 불일치를 확인했다. `data_importer.py`의 Save 패치 BASIC 줄에서 콜론이 누락됐고, `basic_compiler.py`가 Ruby가 단일 바이트로 보존하는 원시 제어 바이트를 UTF-8 2바이트로 인코딩했다.
- 두 부분을 Ruby 소스와 동일하게 수정했다. 수정 후 ASM 12개, `Import/Data` 8개, BASIC·이미지 생성 파일 130개, 플로피 RAW 44개가 Ruby 2.7.4 결과와 모두 일치했으며, 각 비교에서 차이·누락은 0개였다.
- 수정된 Python 포트로 공개 영문 이미지에서 추출한 `02 MIRR.iso`를 다시 처리했다. 현재 기준 플로피는 `python_mirrors_tools/Export/Floppy`의 44개 RAW이며, 각 파일 크기는 409,600바이트다.
- Python·Ruby가 생성한 `02 MIRR.iso`는 모두 40,550,400바이트이고 SHA-256 `447d3f23d81897e040919b89b949814977effefe8ac89252dcf4f51553f411c2`로 동일하다. 공개 영문 이미지에서 추출한 Track 2 기준 파일과도 일치한다.
- 위 결과는 변환 도구의 정적·바이트 검증 결과다. 이어서 사용자가 `Mirrors_korean_500_intro_menu_safe_tokens_test.ccd`를 실행해 메뉴 진입과 한글 출력을 확인했다. 에뮬레이터는 사용자가 직접 실행했으며, 이 작업에서는 실행하지 않았다.
- 현재 작업 트리의 VWF는 처음 작성했던 축약 출력기를 폐기하고 영문판 VWF 합성 경로를 기반으로 복구한 상태다.
- 현재 작업 트리의 로더는 영문판의 `copyFnt = 0x2000` 및 두 번의 4섹터 폰트 로드 구조를 기준으로 복구돼 있다. Ruby·Python 바이트 대조 결과는 영문 기준 빌드의 일치성을 확인한 것이고, 한글 토큰·VWF 시험 이미지의 정상 동작은 아래의 별도 런타임 확인으로 확정했다.
- CloneCD 세트 생성 과정에서 발견된 EDC/ECC LUT 오류는 Python 도구에서 수정됐고, 생성 섹터의 EDC/ECC 정적 검증을 통과했다.
- 현재 격리 이미지 3종의 Track 2 전체 19,800개 Mode1 섹터는 프로젝트 자체 EDC/ECC 검증기를 통과했다. 이는 생성 알고리즘과의 자기 일관성 검사이며, 외부 CD 검증기 또는 에뮬레이터 호환성을 보증하지 않는다.
- 최종 안전 토큰 시험 CloneCD는 Track 2의 19,800개 섹터를 검사했고 패치 섹터는 12개였다. 출력 Track 2의 전체 페이로드가 일치했으며, Track 2 밖의 바이트 차이는 0개이고 `.ccd`·`.sub` 메타데이터도 변경하지 않았다.
- 사용자의 런타임 확인으로 안전 2바이트 토큰, 500자 연속 글리프 상주, 기존 VWF 합성 경로, CloneCD 생성물을 결합한 시험이 메뉴까지 진입하고 한글을 정상 출력하는 것을 확인했다. 따라서 이 시험 범위에서는 VWF·글리프·토큰·CD 섹터 경로가 함께 작동한다.
- 위 500자·뱅크 1 시험은 토큰 소비와 한글 글리프 상주를 확인한 격리 시험이다. 최종 본문 출력은 기존 영문 글리프와 한글 뱅크를 유지하면서 전체 출력 기준점과 16행 줄 간격을 적용한다.
- 생산판 1,093자 구현에서는 가나다순 토큰표 `E040~E5D9`와 1,280슬롯 `0x5000`바이트 글리프 RAW를 사용한다. 1,093개 토큰의 중복·금지 하위 바이트·인덱스 주소를 전수 검사했으며 마지막 글리프는 `0x5440~0x544F`, 첫 예약 공백은 `0x5450`이다.
- 수정 VWF는 778바이트(`0x30A`), 수정 `asmbasic`은 2,339바이트(`0x923`)다. `asmbasic`의 기존 앞쪽 `0x900`바이트는 수정 전 바이너리와 완전히 같고 새 뱅크 1 로더만 뒤에 추가됐다.

- 그래픽 PNG를 바꿨는데도 화면에 이전 이미지가 나타나는 경우, 빌드 오류가 아니라 Drive 1·2에 기존 2HD 데이터가 남아 있을 가능성을 먼저 확인한다. 영문 메뉴는 디스크의 유효한 식별 정보를 확인한 뒤 이미 준비된 디스크이면 `COMMON COPY`를 건너뛸 수 있으므로, 새 그래픽을 시험할 때는 해당 디스크를 초기화·재포맷하거나 새 디스크 이미지로 교체해야 한다.
- 원본 `Mirrors.img`에서 Track 2를 추출했고, Python `export`로 영문 소스가 정의한 44개 2D 플로피 RAW를 생성해 원본 Track 2 구간과 바이트 단위로 대조했다.
- 시험 ISO·CloneCD·RAW·로그·비교 결과 같은 생성 산출물은 계속 `korean_mirrors_tools/Temp`에서 관리하고 Git에는 넣지 않는다. 반면 재현에 필요한 500자 시험용 Python·BASIC·ASM·토큰표·폰트 PNG와 `i_cddata_korean500_test.csv`는 소스 입력이므로 Git에 기록한다. 이 500자 프로필은 생산판 글자 수를 확정하는 자료가 아니라 VWF·토큰·글리프 상주 시험용이다.

- 영문 패치 또는 한글 패치 이미지를 다시 만들 때는 사용자가 별도로 보관한 원본 CD 이미지에서 Track 2를 추출하고, 빌드 도구가 요구하는 44개 플로피 RAW를 로컬 입력 경로에 준비해야 한다.
- 현재 작업 폴더의 `Import/ISO`, `Import/Floppy`, `Export/ISO`, `Export/Floppy`는 이 로컬 입력·생성물 경로이며 Git 배포 대상이 아니다.
- 따라서 저장소만 clone한 환경에서는 원본 이미지가 없어 CD·플로피 데이터를 재구성할 수 없다. 원본 이미지 제공과 추출은 사용자가 보유한 정당한 원본을 기준으로 별도 수행해야 한다.

## 12. 최근 영문 기준 메뉴·NO0·NO1 시험 빌드

영문 패치가 적용된 공개 Track 2를 기준 이미지로 사용하고, 메뉴·NO0·NO1만 한글 번역을 적용하는 격리 시험 빌드를 수행했다. 생성 ISO·RAW·CloneCD는 `korean_mirrors_tools/Temp/english_menu_no0_no1_test/`에서 관리하며 Git에는 넣지 않는다.

### 12.1 입력 소스와 매칭 규칙

- 메뉴는 영문 패치의 `Import/BASIC/menu.bas`를 사용해 영문 패치의 메뉴 제어 흐름과 문자열 분할을 유지한다.
- NO0·NO1은 Ruby 빌드와 동일하게 `Export/BASIC` 원문에 `Data/patchBasic.csv`, VWF 패치, 저장 패치, CD 전환 패치를 순서대로 적용한다.
- 한글 문자열은 BASIC 행 번호만으로 매칭하지 않는다. `source_text`와 `basic_line`을 함께 비교하고, 메뉴처럼 영문 패치에서 원문이 분할된 경우에는 `stringsJapaneseEnglish.csv`의 BASIC 행·문자열 번호 대응과 실제 영문 `menu.bas` 문자열을 함께 사용한다.
- 메뉴 1600행은 영문 패치에서 두 개의 문자열로 분리됐고, 1700행에는 이름 입력 안내문이 들어간다. 이 세 문자열은 분할된 실제 영문 리터럴에 각각 대응시킨다.
- 이 규칙으로 메뉴의 CSV 한글 번역 행 40개를 영문 메뉴 소스에 적용했다. 행 번호만 보고 한 줄의 첫 번째 문자열을 교체하는 임시 매퍼는 폐기했다.

### 12.2 이전 정지 원인과 수정 결과

이전 시험 빌드의 임시 `ByLineCompiler`는 NO1 120행에 문자열이 두 개 있다는 사실을 무시하고 행 번호만으로 번역을 넣었다. 그 결과 시간 문자열 `09:06`이 한글 토큰으로 덮어써져 NO1 시작 직후 진행이 멈췄다.

영문 BASIC을 직접 읽어 한글 CSV를 적용했을 때는 일본어 `source_text`와 영문 리터럴이 일치하지 않아 번역이 빠지는 별도 문제가 발생했다. 현재 시험 빌드는 다음 방식으로 수정했다.

```text
영문 Track 2·2HD 배치 유지
메뉴: 영문 패치 menu.bas + 실제 영문 리터럴별 한글 매핑
NO0·NO1: Export/BASIC 원문 + patchBasic + VWF/저장/CD 패치
문자열 변환: source_text·BASIC 행·문자열 위치 대응
```

정적 대조 결과는 다음과 같다.

- 메뉴 제어 흐름은 영문 기준과 정규화 비교 불일치 0건이다.
- NO0·NO1의 영문 기준과의 차이는 한글 2바이트 토큰을 읽기 위한 VWF 분기 추가뿐이다. NO0의 9005/9007행과 NO1의 5005/5007행이 해당한다.
- NO1 120행의 `COMMON P"09:06"TO"11:52"`와 `CMD LOAD"NAM1",&HF0,&HE4A8`는 그대로 유지된다.
- 메뉴 1200행의 `처음부터 시작하기`, 1210행의 `중간부터 시작하기`, 1214행의 저장 디스크 메뉴가 한글 토큰으로 변환된다.
- disk01·disk02의 BASIC 파일은 각각 144/400, 95/400 섹터가 남는다.
- 기존 영문 IMG를 기반으로 만든 CloneCD의 Track 2 19,800개 섹터가 EDC/ECC 검사를 통과했고, 페이로드 19,800개가 ISO와 일치한다. `.ccd`와 `.sub`는 영문 기준과 동일하다.

### 12.3 CSV 문자열과 하드코딩 문자열의 구분

NO0의 `This story is a work of fiction.`은 CSV 번역문이 아니라 `basic_applyVWFHandler_Opening()`이 BASIC 10010행에 직접 삽입하는 하드코딩 문자열이다. CSV에는 원문이 10010·10011·10012행으로 나뉜 세 개의 한글 번역 행이 존재하지만, 하드코딩 패치가 원문을 먼저 교체하므로 일반 CSV 매칭 대상이 되지 않는다.

따라서 현재 메뉴·NO0·NO1의 정상 진행 여부와 이 오프닝 안내문의 한글화는 별도 과제다. 하드코딩 출력 문자열 6개는 번역표 자체의 오류가 아니며, 최종 하드코딩 한글화 단계에서 `data_importer.py`의 패치 문구를 교체하고 각 BASIC 파일 크기를 다시 검사한다.

### 12.4 현재 시험판과 이전 v2의 차이

현재 유지하는 시험 산출물은 `korean_mirrors_tools/Temp/english_menu_no0_no1_test/`다. 이전 `english_menu_no0_no1_test_v2` 산출물은 비교 후 삭제했다.

두 시험판을 바이트 단위로 비교한 결과는 다음과 같다.

- `vwf.raw`는 778바이트로 완전히 동일하다.
- `asmbasic.raw` 2,339바이트와 `asmsub.raw`도 동일하다.
- 메뉴·NO0·NO1의 `data`와 `floppy/disk01.raw`, `floppy/disk02.raw`도 동일하다.
- 출력 ISO 크기는 모두 40,550,400바이트이며, 두 ISO의 차이는 Track 2 ISO 섹터 4 하나뿐이다. CloneCD RAW 기준으로는 raw 섹터 13,354 하나다.

차이가 난 섹터 4는 V2 모드와 8MHz 확인용 하드코딩 안내문이다. v2에는 다음 영문 문장이 남아 있었다.

```basic
BM$="Please change to V2 Mode."
BM$="Please change speed to 8Mz."
```

현재 시험판에서는 이 안내문이 한글 토큰을 포함한 문장으로 바뀌었다. 따라서 현재판의 본문 상단 비잘림은 VWF 바이너리가 새로 바뀌어서 발생한 것이 아니다. 두 판 모두 본문 16행 프로필과 `BN=BN+&H50*16` 행 이동을 사용하며, 현재판의 성공 차이는 초기 하드코딩 안내문 섹터에서 발생한다.

이 비교는 메뉴·NO0·NO1 시험 범위의 원인 분리에 대한 기록이다. 전체 게임의 모든 하드코딩 안내문과 UI 설명문이 한글화됐다는 뜻은 아니다.
