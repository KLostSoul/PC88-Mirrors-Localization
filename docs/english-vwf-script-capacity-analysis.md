# 영문 패치 VWF·문자열·스크립트 실측 분석

분석 기준: 원본 이미지, 공개 영문 패치 이미지, 저장소의 Ruby 원본 소스와 영문 패치 입력 소스. 에뮬레이터는 실행하지 않았다.

이 문서는 한글 번역문이 아직 확정되지 않은 상태에서, 한글 토큰·글리프·VWF를 적용할 때 필요한 영문판의 실제 동작과 용량 기준을 확정하기 위한 정적 분석 결과다. 소스에 적힌 추정값보다 이미지에서 직접 읽은 BASIC/ASM/폰트/디스크 데이터를 우선한다.

## 1. 분석 대상과 이미지 검증

대상 파일은 다음과 같다.

- 원본 CloneCD 이미지: `reference/Original/Mirrors.img`
- 공개 영문 패치 이미지: `reference/Mirrors PC-8801 MC English translation v1.0 (updated emu)/Mirrors eng v1.0.img`
- 원본 추출·디컴파일 결과: `reference/mirrors_tools/Export`
- 영문 패치 빌드 입력: `reference/mirrors_tools/Import`
- 주소·스크립트·디스크 배치표: `reference/mirrors_tools/Data`

CloneCD 이미지에서 CD 데이터 트랙을 다음 방식으로 추출해 비교했다.

- 데이터 시작 LBA: `13350`
- Mode 1 raw 섹터 크기: `2352`바이트
- 섹터 payload: raw 섹터의 +16 위치부터 `2048`바이트
- 데이터 섹터 수: `19,800`
- Track 2 payload 크기: `40,550,400`바이트

| 기준 | SHA-256 |
|---|---|
| 원본 Track 2 | `e53f8331c3b3670dcc26b8e7f3762915a3e62014858221e9c9575e5cbc180188` |
| 영문 패치 Track 2 | `447d3f23d81897e040919b89b949814977effefe8ac89252dcf4f51553f411c2` |

두 Track 2의 전체 차이 바이트는 `17,903,701`바이트다. 이는 BASIC 문자열만 바뀐 결과가 아니라 2HD 재배치·플로피 재패킹·ASM/VWF·폰트·그래픽을 모두 포함한 차이다.

## 2. 가장 중요한 결론

1. 원본 게임의 기존 JIS VWF와 영문 패치의 실제 출력 엔진은 분리해서 봐야 한다. 원본 `Export/ASM/asmmain.asm`의 JIS 루틴은 2바이트 문자를 처리하지만, 영문 패치는 `LB420 → LB52F → 확장 RAM 0x0000` 경로로 별도 `vwf.asm`을 호출한다.
2. 영문 패치의 `vwf.asm`은 현재 1바이트 단위로 입력 문자열을 읽는다. `_nextSymbol`은 한 번에 한 바이트를 읽고 포인터를 1 증가시키며, `0x0D`만 줄바꿈으로 특별 처리한다.
3. 영문 폰트 생성기는 PNG 하나당 96글리프를 만든다. 글리프 raw 실제 길이는 `96 × 16 = 0x600`바이트이고 폭 테이블은 `0x60`바이트다. `i_cddata.csv`의 `0xC00`은 덮어쓸 수 있는 예약 범위이지 현재 생성되는 글리프 파일의 실제 길이가 아니다.
4. 영문판 105개 논리 BASIC 스크립트는 이미지에서 모두 매칭되며, 영문 코드 본문 합계는 일본판보다 `10,160`바이트 작다. 하지만 스크립트별 여유는 합산해서 사용할 수 없다.
5. 영문판에서 가장 큰 스크립트는 `disk40/NO81`의 `12,264`바이트로, 도구의 `0x3000 = 12,288`바이트 경고 기준보다 겨우 `24`바이트 작다. `NO80`도 `28`바이트 여유뿐이다. 한글 토큰 적용 때 이 두 스크립트부터 분할·축약 후보로 관리해야 한다.
6. 기존 문서의 `+31,887`바이트는 문자열 대조표와 가정식을 이용한 모델값이다. 실제 이미지에 저장된 105개 스크립트의 인용 문자열 payload는 일본판 `410,704`바이트, 영문판 `408,421`바이트로 영문판이 `2,283`바이트 작다. 두 수치는 측정 대상이 다르므로 혼용하면 안 된다.

## 3. 원본 VWF와 영문 패치 VWF의 분리

### 3.1 원본에 남아 있는 JIS VWF

원본 Track 2에서 추출한 `Export/ASM/asmmain.asm`에는 `LB558`와 `LB5FD`를 중심으로 한 기존 문자 루틴이 있다.

- `LB558`은 `D/E` 두 바이트를 읽고 `dec C`를 두 번 수행한다.
- `LB5FD`는 JIS 리드 바이트 범위 `0x81~0x9F`, `0xE0~0xEF`와 트레일 바이트 범위 `0x40~0x7E`, `0x80~0xFC`를 보정한다.
- 이는 원판의 일본어 Kanji ROM 문자 주소 계산 경로다.

이 루틴이 존재한다는 사실만으로 영문 패치의 화면 출력이 이 루틴을 그대로 사용한다고 판단하면 안 된다.

### 3.2 영문 패치가 실제로 호출하는 경로

영문 패치 입력 `Import/ASM_Source/asmmain.asm`에서는 다음과 같이 바뀐다.

```asm
LB420:  jp      LB52F

LB52F:
        ; 확장 RAM 뱅크 0x11 선택
        out     (0xe2),a
        out     (0xe3),a
        call    0x0000    ; 확장 RAM에 적재된 vwf.asm
        ; 뱅크 복구
```

실제 세부 레지스터 값은 소스의 `LB52F`에 있으며, `E2=0x11`, `E3=0`, 호출 주소는 `0x0000`이다. 따라서 영문판의 VWF 출력은 원본 JIS 루틴의 결과가 아니라 확장 RAM에 적재한 별도 엔진의 결과다.

### 3.3 영문 `vwf.asm`의 실제 입력 단위

`Import/ASM_Source/vwf.asm`의 `_nextSymbol`은 다음 순서다.

```asm
ld      hl,(vStrAddr)
ld      e,(hl)          ; 문자 1바이트
ld      d,0
dec     c
inc     hl
ld      (vStrAddr),hl
ld      a,e
cp      0x0d            ; CR만 줄바꿈
call    getRightMargin
call    convertASCII_toCharAddr
```

따라서 현재 영문 엔진의 단위는 다음과 같다.

- 입력 문자: 1바이트
- 문자열 포인터 증가: 1바이트
- `vStrLen`: 현재는 입력 바이트 수를 기준으로 감소
- `vCharCount`: 한 줄의 시각적 문자 처리 수
- `0x0D`: 줄바꿈
- 그 밖의 제어·2바이트 토큰: 현재 엔진의 정상 입력 규격이 아님

한글 2바이트 토큰을 넣으려면 `_nextSymbol`에서 먼저 토큰 하나를 완성한 뒤, 토큰 단위로 길이와 글리프 인덱스를 갱신해야 한다. 기존 JIS 보정 루틴을 그대로 재사용하는 것과는 다른 작업이다.

## 4. VWF 메모리·폰트 배치

### 4.1 초기 로더의 실제 복사 단위

`intro.bas`와 `asmbasic.asm`에서 확인되는 초기 로드는 다음과 같다.

```basic
COMMON R,13382,&HA300,&H4
A=&H92BC:CALL A

COMMON R,13386,&HA300,&H4
POKE &H92C9,&H00:POKE &H92CA,&H20
A=&H92BC:CALL A
```

Track 2 오프셋으로 환산하면 첫 로드는 `0x10000`, 두 번째 로드는 `0x12000`이다. `&H4`는 0x800바이트 섹터 4개, 즉 `0x2000`바이트다.

`copyFnt`는 다음을 수행한다.

- 확장 RAM 뱅크 `0x11` 선택
- `HL=0xA300`
- `DE=0x0000` 또는 두 번째 호출에서 POKE로 `0x2000`
- `BC=0x2000`
- `LDIR`
- 뱅크 복구

결과적인 확장 RAM 배치는 다음과 같다.

| Track 2 범위 | CPU RAM 임시 범위 | 확장 RAM 목적지 |
|---|---|---|
| `0x10000~0x11FFF` | `0xA300~0xC2FF` | `0x0000~0x1FFF` |
| `0x12000~0x13FFF` | `0xA300~0xC2FF` | `0x2000~0x3FFF` |

따라서 `0x3000`은 한 번에 CPU RAM으로 읽는 크기가 아니다. 기존 로더는 `0x2000`씩 두 번 읽고 복사한다.

### 4.2 영문 폰트 슬롯과 주소

`vwf.asm`의 주소 계산은 다음과 같다.

```text
font_base = vFontNumber << 12
glyph_address = font_base + (input_byte - 0x20) * 0x10
right_margin_base = font_base + 0x0F00
```

폭 조회는 `convertASCII_toCharAddr`보다 먼저 수행되며, 그 시점의 `E`는 정규화 전 원본 ASCII 바이트다. 그래서 화면 출력 ASCII `0x20~0x7F`의 폭은 실제로 `font_base + 0x0F20~0x0F7F`에서 읽힌다.

| 뱅크 | 실제 글리프 영역 | 폭 테이블 | 용도 |
|---:|---|---|---|
| 1 | `0x1000~0x15FF` | `0x1F20~0x1F7F` | script |
| 2 | `0x2000~0x25FF` | `0x2F20~0x2F7F` | UI |
| 3 | `0x3000~0x35FF` | `0x3F20~0x3F7F` | menu |

각 폰트 뱅크에는 `0x600`바이트의 실제 글리프, `0x60`바이트의 폭 테이블, 그리고 VWF가 현재 사용하지 않는 예약·간격 영역이 있다. `i_cddata.csv`는 각 글리프 파일에 `0xC00`의 덮어쓰기 범위를 선언하지만, 현재 `FontGen.rb`가 생성하는 파일은 `0x600`바이트다. 이미지에서도 각 `*_bytes.raw`의 첫 `0x600`바이트는 생성 raw와 일치한다.

### 4.3 FontGen의 정확한 입력 형식

`Ruby/FontGen.rb`는 다음 규칙으로 PNG를 raw로 바꾼다.

- 셀 크기: 8×16픽셀
- PNG 크기: 현재 폰트 PNG는 128×256
- 위에서 두 셀 행을 건너뜀
- 6행 × 16열 = 96글리프
- 글리프 하나: 16바이트
- 폭 테이블: 96바이트
- 좌우 빈 열을 최대 4열까지 잘라 가변 폭 계산
- 첫 슬롯 폭은 `0x02`로 강제

현재 영문 슬롯은 `0x20~0x7F` 96개이며, 표준 출력 ASCII만 세면 `0x20~0x7E` 95개다. 세 폰트 뱅크는 같은 슬롯 번호를 재사용한다. 따라서 96×3=288은 하나의 288자 문자표가 아니라 용도별 96슬롯 세 개다.

## 5. BASIC·VWF 문자열 처리 규칙

### 5.1 컴파일러

`Ruby/BasicCompiler.rb`는 다음을 수행한다.

- BASIC 예약어·확장 예약어를 토큰 바이트로 변환
- 인용부호 문자열을 번역표의 `source_text`와 `basic_line`로 매칭
- script 문자열은 `script_widths.raw` 기준 픽셀 폭으로 단어 단위 줄바꿈
- 한 줄 폭 기준은 `LineLimit = 362`
- 긴 문자열은 백슬래시와 BASIC 제어 시퀀스를 넣어 여러 화면 줄로 나눔
- 한 BASIC 라인에 대해 번역·패치·토큰·라인 헤더까지 합친 결과가 실제 코드 크기가 됨

`@widthData[l.ord - 0x20]`와 같은 ASCII 직접 인덱싱은 한글 토큰에 그대로 사용할 수 없다. 한글판에서는 문자의 표시 폭과 저장 토큰 바이트 수를 분리해야 한다.

또한 Ruby 컴파일러가 긴 문자열 처리 중 넣는 `0x3A,0x8D,0x20,0x0E,0xEC,0x13,0x3A,0x42,0x4D,0x24,0xF1`은 화면에 표시하는 글리프가 아니라 BASIC 실행 제어 시퀀스다. 한글 토큰 바이트와 혼동해서는 안 된다.

### 5.2 스크립트별 VWF 핸들러 적용

`e_scripts.csv` 기준 105개 스크립트의 설정은 다음과 같다.

- `commonPatch=true`: 102개
- `allowSave=true`: 100개
- `splitPoints` 지정: 7개
- 특수 처리:
  - `NO0`: opening 전용 VWF 패치를 별도로 삽입
  - `LIV1`: 공통 VWF 패치 없음
  - `END`: 공통 VWF 패치 없음
  - `NO10`, `NO28`: VWF는 적용되지만 Save 패치는 없음

공통 VWF 핸들러는 다음과 같은 BASIC을 삽입한다.

```basic
FOR K1=1 TO LEN(BM$)
 K$=MID$(BM$,K1,1)
 CMD WIDTH BN,&H60,7
 POKE &HB400,1
 CMD KANJI K$
NEXT
```

이 루틴은 영문에서는 ASCII 1바이트를 전제로 한다. 한글 2바이트 토큰을 최종 문자열에 넣으려면 `LEN/MID$/ASC` 부분도 토큰 단위로 바꾸거나, 문자열 전체를 VWF에 넘기는 별도 경로를 확정해야 한다. VWF 내부만 고쳐서는 이 BASIC 핸들러가 토큰을 두 조각으로 나누는 문제가 해결되지 않는다.

## 6. 실제 이미지의 BASIC 용량 측정

스크립트는 원본·영문 Track 2의 실제 2D 디스크 디렉터리에서 파일을 찾아 직접 읽었다. 파일 헤더의 코드 길이, 디렉터리 map의 물리 섹터 수, BASIC line chain, 인용부호 문자열을 각각 따로 계산했다.

### 6.1 105개 스크립트 합계

| 항목 | 원본 일본판 | 영문 패치 | 영문-원본 |
|---|---:|---:|---:|
| 코드 본문 | 931,738 | 921,578 | -10,160 |
| 물리 디스크 할당 | 1,148,928 | 973,824 | -175,104 |
| BASIC line 수 | 16,958 | 16,753 | -205 |
| 인용 문자열 수 | 9,743 | 9,146 | -597 |
| 인용 문자열 payload | 410,704 | 408,421 | -2,283 |

물리 디스크 할당은 실제 디렉터리 map의 섹터 수다. 원본은 파일이 과거 섹터를 넉넉하게 점유한 경우가 많고, 영문 패치는 재패킹하면서 코드 길이에 맞춰 밀집 배치한다. 따라서 코드 본문 합계와 물리 할당 합계를 같은 값으로 취급하면 안 된다.

영문 스크립트 코드의 `0x3000` 기준 누적 여유는 다음과 같다.

```text
105 × 0x3000 - 921,578 = 368,662바이트
```

이 값은 스크립트 사이에서 이동할 수 있는 공용 여유가 아니다. 각 BASIC 파일이 개별적으로 한도를 넘지 않아야 한다. 현재 영문판의 물리 할당은 코드 본문과 7바이트 헤더를 포함한 섹터 올림 결과이며, 총 섹터 패딩은 `51,511`바이트다.

### 6.3 Intro·menu

Intro와 menu는 일반 플로피 BASIC 파일과 달리 Track 2의 고정 영역에 직접 들어간다.

| 영역 | Track 2 예약 크기 | 원본 인용 문자열 payload | 영문 인용 문자열 payload |
|---|---:|---:|---:|
| intro | 646 | 62 | 25 |
| menu | 13,510 | 1,996 | 1,470 |

영문 `Import/Data/menu.raw`의 실제 생성 파일 길이는 11,140바이트이며, Track 2 menu 예약 범위는 13,510바이트다. 컴파일 결과 뒤의 예약 꼬리 영역은 이미지에서 그대로 남을 수 있으므로, 논리 BASIC 종료와 CSV 예약 크기를 구분해야 한다.

## 8. 한글화에 적용해야 하는 정확한 조건

### 8.1 토큰·VWF

한글 2바이트 토큰을 적용할 때 최소 수정 대상은 다음 네 곳이다.

1. `vwf.asm/_nextSymbol`: 1바이트 읽기를 2바이트 토큰 판독으로 변경
2. 토큰의 두 바이트를 글리프 인덱스로 변환하고 `glyph_base + index × 16` 계산
3. `vStrLen`을 입력 바이트 수와 표시 글리프 수 중 무엇으로 사용할지 분리
4. `getRightMargin`을 토큰 해석 후 호출하거나, 토큰에 맞는 고정 8픽셀 폭을 직접 적용

현재 영문 엔진은 폭을 원본 ASCII 바이트로 조회한 뒤 글리프 주소만 `0x20`을 빼서 계산한다. 한글 토큰의 상위·하위 바이트가 그대로 이 경로에 들어가면 폭 테이블·글리프 주소 모두 잘못된다.

### 8.2 글리프 용량

8×16 1비트 글리프의 실제 크기는 다음과 같다.

| 글리프 수 | 글리프 raw | 폭 테이블까지 포함 |
|---:|---:|---:|
| 96 | 1,536 (`0x600`) | 1,632 (`0x660`) |
| 500 | 8,000 (`0x1F40`) | 8,500 (`0x2134`) |
| 600 | 9,600 (`0x2580`) | 10,200 (`0x27D8`) |

현재 영문 확장 RAM의 글리프 뱅크는 script/UI/menu로 나뉘어 있다. 500자 글리프 `0x1F40`바이트는 script 뱅크 하나에 들어가지 않으며 script와 UI 영역을 가로지른다. 따라서 다음 중 하나를 명시적으로 선택해야 한다.

- UI/menu 폰트 영역을 한글 글리프 페이지로 재사용하고 ASCII/UI 출력 요구를 별도 처리
- 글리프 페이지 번호를 추가해 확장 RAM의 다른 영역을 선택
- 한글 글리프와 폭 테이블을 기존 3뱅크 배치와 다른 연속 영역에 재배치하고 로더·`vFontNumber`·주소 계산을 함께 수정

단순히 PNG를 500칸으로 늘리고 `i_cddata.csv`의 기존 96슬롯 주소에 덮어쓰는 것은 안전한 변경이 아니다.

### 8.3 스크립트 용량 산정식

최종 번역문이 정해지면 스크립트 `s`마다 다음 값을 계산해야 한다.

```text
final_code_s
  = English_code_s
  - English_display_payload_replaced
  + Korean_token_payload
  + compiler/VWF_handler_extra_s
```

여기서 `Korean_token_payload`는 최종 토큰 규칙에 따라 계산해야 한다. 한글 글자만 2바이트인지, ASCII·공백·기호도 2바이트 토큰으로 통일하는지, 키 입력 판정 문자열을 그대로 둘지에 따라 값이 달라진다.

마지막으로 다음을 모두 개별 검사해야 한다.

- `final_code_s <= 0x3000`
- 파일의 실제 섹터 할당과 디스크 디렉터리 map
- `splitPoints`를 가진 7개 스크립트의 두 파일 결과
- `CMD WIDTH` 줄 폭과 실제 한글 표시 폭
- `LEN/MID$/ASC`가 토큰을 분리하지 않는지
- `0x0D`·BASIC 예약 토큰·VWF 제어 시퀀스와 한글 토큰이 충돌하지 않는지
- menu/intro의 고정 Track 2 영역과 컴파일 종료 위치

## 9. 분석 결과의 사용 기준

이 문서의 105행 표는 영문 이미지에서 직접 읽은 기준선이다. 한글 번역표가 만들어지면 동일한 분석기를 다시 실행해 각 행의 `English code`, `Korean code`, `headroom`, `physical sectors`를 비교해야 한다.

특히 기존 문서의 대조표 기반 `+31,887`은 번역표 레코드의 이론 모델로 남겨두되, 실제 영문 이미지의 총 BASIC 용량을 나타내는 값으로 사용하지 않는다. 실제 바이너리 기준값은 이 문서의 Track 2·디렉터리·BASIC line chain 실측값이다.
