# 문자열 바이트 용량 재계산

> 주의: 이 문서는 문자열 대조표 레코드와 가정식을 이용한 모델 계산이다. 실제 원본·영문 이미지의 BASIC 파일, 디렉터리 할당, 인용 문자열 payload를 직접 읽은 최신 기준값은 [`docs/english-vwf-script-capacity-analysis.md`](english-vwf-script-capacity-analysis.md)에서 확인한다. 이 문서의 `+31,887`은 실제 Track 2 전체 또는 105개 스크립트 바이너리의 증감값이 아니다.

## 1. 목적

일본어 원문과 영문 패치의 문자열 저장 용량을 다시 계산한다. 이전 계산에서 일본어 원문을 Shift-JIS 실제 바이트 수로 계산했으나, PC-88 원판의 표시 문자열은 칸지롬 문자 토큰을 사용한다. 따라서 이번 문서는 표시 토큰 기준으로 다시 산출한 결과다.

이 문서는 한글 번역 완료 후의 최종 용량이 아니라, 한글화 설계에 사용할 기준값을 확정하기 위한 정적 분석 결과다.

## 2. 계산 기준

### 2.1 일본어 표시 문자열

칸지롬을 통해 화면에 표시되는 문자는 다음과 같이 계산한다.

- 일본어 한자·가나: 문자 토큰 2바이트
- 숫자·영문·공백·구두점·기호: 표시 문자 토큰 2바이트
- 문자열을 감싸는 BASIC 인용부호: 2바이트

즉, 일본어 원문 문자열의 기본 크기는 다음과 같다.

    일본어 레코드 크기 = (표시 문자 수 × 2) + 인용부호 2바이트

여기서 표시 토큰과 BASIC 문법·제어 바이트는 구분한다. 문자열 내부의 표시 문자는 칸지롬 토큰으로 계산하지만, 줄 연결·VWF 처리 등에 사용되는 제어 바이트는 별도로 계산한다.

### 2.2 영문 패치 문자열

영문 패치의 저장 크기는 영문 소스의 실제 컴파일 규칙을 기준으로 모델링했다.

- 영문 표시 문자: 1바이트
- 문자열 인용부호: 2바이트
- 스크립트별 줄 폭과 줄바꿈: script_widths.raw 기준
- BASIC 줄 연결 및 VWF 제어 시퀀스: BasicCompiler.rb의 기존 처리 규칙 반영
- 영문 패치에서 번역되지 않은 문자열: 일본어 원문 레코드 크기 유지
- 원문에만 존재하는 행: 영문 패치 대상 합계에서 제외
- 동일 디스크 중복 행: 패치에 포함된 레코드로 계산

### 2.3 대조 데이터

- 문자열 대조표: korean_mirrors_tools/Export/Strings/stringsJapaneseEnglish.csv
- 스크립트 폭 정보: korean_mirrors_tools/Import/Data/script_widths.raw
- 영문 컴파일 규칙: korean_mirrors_tools/Export/Basic/BasicCompiler.rb

## 3. 대조표 상태

전체 대조표는 9,724행이다.

| 상태 | 행 수 | 의미 |
|---|---:|---|

## 4. 칸지롬 기준 재계산 결과

일본어 표시 문자를 전부 2바이트 칸지롬 토큰으로 계산한 결과다. 영문 수치는 영문 패치의 컴파일·줄바꿈·제어 시퀀스 규칙을 적용한 모델값이다.

| 구분 | 행 수 | 일본어 원문 | 영문 패치 | 차이 |
|---|---:|---:|---:|---:|
| matched_translated | 4,979 | 379,152 | 411,019 | +31,867 |
| matched_empty | 299 | 16,324 | 16,324 | 0 |
| patch_duplicate | 4 | 262 | 282 | +20 |
| **영문 패치 대상 합계** | **5,282** | **395,738** | **427,625** | **+31,887** |

따라서 영문 패치 대상 문자열 레코드만 비교하면 영문 패치가 일본어 칸지롬 기준보다 31,887바이트 크다.

이 값은 전체 Track 2 이미지의 크기 차이나 한글 번역 후의 최종 크기가 아니다. 문자열 레코드에 대한 비교값이며, 프로그램 코드·디렉터리·파일 시스템·이미지 여유 공간은 포함하지 않는다.

### 4.1 원본 Track 2 초반부 실측 검증

전체 합계는 대조표와 컴파일 규칙을 이용한 모델 계산이지만, 초반부의 실제 문자열 저장값은 원본 Track 2에서 직접 확인했다.

- 기준 Track 2: reference/mirrors_tools/Export/ISO/02 MIRR.iso
- intro 영역: Track 2 오프셋 0x2000, 646바이트
- menu 영역: Track 2 오프셋 0x8000, 13,510바이트
- intro.raw와 menu.raw는 각각 해당 Track 2 영역과 전체 바이트 및 SHA-256이 일치한다.

| 영역 | BASIC 줄 | 실제 저장 바이트 | 문자 수 | 칸지롬 2바이트 계산 |

초반 화면 표시 문자열에서는 전각 숫자·공백·구두점·기호도 모두 2바이트로 저장되어 칸지롬 모델과 일치했다. menu의 n/N/y/Y는 화면에 표시하는 값이 아니라 INKEY$ 키보드 입력 비교용 ASCII 문자열이므로 1바이트다.

## 5. 행별 증감

번역된 행과 중복 행을 합친 4,983행을 비교했다.

| 결과 | 행 수 |
|---|---:|
| 영문 쪽이 증가 | 2,553 |
| 영문 쪽이 감소 | 2,335 |
| 동일 | 95 |

행별 차이는 다음 범위였다.

- 최소: -86바이트
- 최대: +179바이트
- 평균: +6.399바이트

영문 패치가 전체적으로 증가했지만, 모든 행이 증가한 것은 아니다. 원문의 표시 문자 수가 많고 영문 번역이 짧은 행은 영문 쪽이 더 작다.

## 8. 한글화에 적용할 결론

1. 일본어 원문 표시 문자를 계산할 때 숫자·영문·공백·부호를 1바이트로 예외 처리하면 안 된다. 칸지롬 표시 토큰이면 모두 2바이트다.
2. 이전의 Shift-JIS 실제 바이트 기준 수치 +33,198바이트는 이번 기준에 맞지 않으므로 폐기한다.
3. 현재 확정된 비교 기준은 일본어 칸지롬 표시 토큰 기준 대비 영문 패치 대상 문자열 레코드 +31,887바이트다.
4. 한글도 최종적으로는 한글 표시 토큰 하나를 2바이트로 계산한다.
5. 한글 번역문이 짧아지면 영문 패치보다 작아질 수 있으므로 영문보다 항상 커진다고 단정할 수 없다.
6. 한글 최종 용량은 다음 항목을 모두 반영해 번역표가 작성된 뒤 다시 계산해야 한다.

       한글 레코드 크기
       = (한글 표시 토큰 수 × 2)
       + BASIC 문자열·줄 연결 오버헤드
       + VWF 제어 바이트

7. 최종 검사는 문자열 레코드뿐 아니라 각 BASIC 파일의 컴파일 결과와 기존 메모리·파일 크기 제한을 함께 확인해야 한다.

## 9. 주의사항

이 문서의 전체 일본어 합계는 칸지롬 표시 토큰 모델로 계산한 값이며, 초반부 표는 원본 Track 2에서 직접 추출해 확인한 실제 저장 바이트다. 영문 쪽은 영문 표시 토큰 1바이트와 영문 패치의 실제 저장 규칙을 적용했기 때문에, 전체 합계는 동일한 인코딩의 파일 바이트를 단순 비교한 값이 아니다.

또한 이 문서는 정적 문자열 용량 분석이다. 한글 번역표가 확정되면 동일한 방식으로 한글 토큰 수·줄바꿈·제어 시퀀스를 다시 계산하고, 실제 BASIC 산출물의 파일 크기와 이미지 배치 가능 여부를 별도로 확인해야 한다.
