# 한글 조합 글리프 VWF 분석

이 문서는 현재 `korean_mirrors_tools` 정식 빌드에 들어 있는 한글 조합 글리프용 VWF의 실제 구조와 Python 컴파일러의 입력 계약을 기록한다. 설계 제안이나 과거 시험판의 설명이 아니라, 현재 소스와 현재 토큰·RAW 입력을 기준으로 작성한다.

## 1. 분석 대상

현재 기준 파일은 다음과 같다.

- [VWF ASM](../korean_mirrors_tools/Import/ASM_Source/vwf.asm)
- [메인 ASM 호출 게이트](../korean_mirrors_tools/Import/ASM_Source/asmmain.asm)
- [BASIC 초기화·데이터 복사 ASM](../korean_mirrors_tools/Import/ASM_Source/asmbasic.asm)
- [Python BASIC 컴파일러](../korean_mirrors_tools/python_tools/basic_compiler.py)
- [토큰표 생성기](../korean_mirrors_tools/python_tools/generate_korean_token_table.py)
- [현재 한글 토큰표](../korean_mirrors_tools/Data/korean_token_table.csv)
- [CD 데이터 배치표](../korean_mirrors_tools/Data/i_cddata.csv)
- [ASCII 원본](../Composite_16x16/source/ascii_8x16_template.fnt)
- [도깨비 조합 글리프 원본](../Composite_16x16/source/han_dkby.fnt)

현재 VWF는 과거의 3종 영문 폰트 선택 방식이나 `vFontNumber`를 사용하지 않는다. ASCII와 한글 모두 물리 확장 RAM bank 0에 배치된 단일 조합 출력 구조를 사용한다.

## 2. 전체 처리 흐름

문자열은 다음 경로로 처리된다.

```text
번역 문자열
  → Python 컴파일러가 한글 문자를 2바이트 토큰으로 직렬화
  → BASIC 문자열/제어 스트림 생성
  → CMD KANJI 또는 직접 호출 경로
  → LB52F의 bank 0 VWF 호출 게이트
  → vwf.asm의 문자 판별
  → ASCII 글리프 복사 또는 한글 자모 컴포넌트 조합
  → 16행 출력
```

VWF의 문자 판별 순서는 다음과 같다.

1. 현재 바이트가 `0x80` 미만이면 일반 1바이트 문자 경로를 검사한다.
2. `0x80` 이상이면 토큰 선두표에서 유효한 한글 선두인지 검사한다.
3. 유효한 선두이면 다음 바이트를 토큰 후행으로 소비하고 한글을 조합한다.
4. 유효한 선두가 아니면 1바이트 경로로 처리한다.
5. 1바이트 경로에서 `0x5C` 또는 `0x0D`는 줄바꿈 제어로 처리한다.

따라서 제어 바이트를 숫자 범위만으로 한글 또는 공백으로 바꾸지 않는다. 선두표와 후행표, 줄바꿈 검사, BASIC 제어 토큰 처리가 각각 분리되어 있다.

## 3. 토큰 형식

### 3.1 현재 토큰표

`korean_token_table.csv`의 현재 행 수는 1,100개다. 이 수는 고정된 1,093개 슬롯이 아니라 현재 번역 문자열과 하드코딩 문자열에서 수집된 한글 음절 수에 따라 생성된다.

토큰표의 주요 필드는 다음과 같다.

```text
token_index
character
unicode
token_word
token_hi
token_lo
initial_index
medial_index
final_index
composition_payload
```

생성기는 다음 입력에서 한글 음절을 수집한다.

- `Import/Strings/stringsImportK.csv`
- `Data/hardcoded_strings.csv`
- `Data/patchBasic.csv`

수집된 음절은 Unicode 순으로 정렬된다. 따라서 새 번역 문자열이나 하드코딩 문자열에 새 음절이 들어오면 토큰표를 다시 생성할 때 전체 가나다순 인덱스가 다시 계산된다.

### 3.2 토큰 바이트 공간

현재 생성 규칙은 BASIC 및 VWF 제어 바이트와 충돌하지 않도록 선두와 후행을 별도로 제한한다.

- 선두 후보: `0x80~0xDF` 중 제어 바이트를 제외한 75개
- 후행 후보: `0x40~0x7E`, `0x80~0xFC` 중 후행 제어 바이트를 제외한 165개
- 현재 표의 첫 토큰: `가 = 0x8040`
- 현재 표의 마지막 토큰: `힘 = 0xD0B8`

토큰 인덱스는 다음처럼 계산된다.

```text
lead_index  = token_index // 165
trail_index = token_index % 165
token_hi    = safe_leads[lead_index]
token_lo    = safe_trails[trail_index]
```

현재 실제 표에서 사용된 선두 바이트 수는 68개이며, 구현 가능한 선두표 전체 용량은 75개다. 후행표는 165개 항목을 사용한다.

Python 컴파일러는 CSV의 `token_hi`, `token_lo`, `composition_payload`를 계산 결과와 비교한다. 인덱스 순서, Unicode 조합값, 토큰 바이트, 제어 바이트 충돌, 중복 글리프가 맞지 않으면 빌드를 중단한다.

## 4. 한글 조합 계산

VWF는 완성 음절 자체의 16×16 RAW를 찾지 않는다. 토큰의 선두·후행 위치에서 음절 인덱스를 얻고, 이를 현대 한글 조합 인덱스로 분해한다.

```text
syllable_index = lead_index * 165 + trail_index

initial_index = syllable_index / 588
remainder     = syllable_index % 588
medial_index  = remainder / 28
final_index   = remainder % 28
```

유효 범위는 다음과 같다.

```text
initial_index: 0..18
medial_index:  0..20
final_index:   0..27
```

현대 한글 전체 범위인 11,172를 넘는 인덱스는 조합하지 않는다. 초성 19개, 중성 21개, 종성 28개 범위를 벗어나는 경우도 무효로 처리한다.

## 5. 8×4×4 컴포넌트 배치

원본 [han_dkby.fnt](../Composite_16x16/source/han_dkby.fnt)은 32바이트 셀을 360개 제공한다. 한 셀은 16행×2바이트인 16×16 1bpp 글리프다.

컴포넌트 영역은 bank 0에서 다음 기준으로 계산된다.

```text
초성 영역: 0x2000
중성 영역: 0x3400
종성 영역: 0x3F00
셀 크기:   32바이트
```

벌별 셀 수와 영역 크기는 다음과 같다.

| 영역 | 벌 수 | 셀 수 | 크기 |
|---|---:|---:|---:|
| 초성 | 8 | 8×20 = 160 | 0x1400 |
| 중성 | 4 | 4×22 = 88 | 0x0B00 |
| 종성 | 4 | 4×28 = 112 | 0x0E00 |
| 합계 | 16 | 360 | 0x2D00 |

주소 계산은 다음과 같다.

```text
초성 = 0x2000 + ((initial_profile * 20) + (initial_index + 1)) * 32
중성 = 0x3400 + ((medial_profile  * 22) + (medial_index  + 1)) * 32
종성 = 0x3F00 + ((final_profile   * 28) + final_index)       * 32
```

초성의 `+1`과 중성의 `+1`은 각 벌의 첫 셀 배치 규칙에 따른다. 종성은 무받침 값인 `final_index=0`을 건너뛰고 실제 종성 셀을 사용한다.

벌 선택은 VWF의 프로필 배열에서 결정된다.

- 무받침/받침 초성 프로필 배열
- 중성의 무받침/받침 프로필과 좌우형 보정
- 중성 형태에 따른 종성 프로필 배열

VWF는 세 컴포넌트를 같은 32바이트 버퍼에 OR한다. 종성 인덱스가 0이면 종성 OR 단계는 생략한다.

## 6. bank 0과 CD 배치

### 6.1 런타임 bank 0 주소

VWF 주석과 주소 계산 기준은 다음과 같다.

```text
0x0000~0x0FFF : VWF 코드와 VWF 상태/버퍼
0x1000~0x1FFF : ASCII 8×16 원본 영역
0x2000~0x4CFF : 8×4×4 한글 컴포넌트 360셀
0x4D00~0x7FFF : 현재 컴포넌트 영역 이후의 여유 영역
```

ASCII 주소는 다음처럼 계산된다.

```text
glyph_address = 0x1000 + ASCII_code * 16
```

실제 출력 대상은 `0x20~0x7F`이며, ASCII 셀 하나는 16바이트다. ASCII는 한 셀, 즉 화면 메모리 한 바이트 폭을 전진한다.

### 6.2 CD 데이터

현재 `i_cddata.csv`의 조합 글리프 데이터 배치는 다음과 같다.

```text
0x10000~0x10FFF : vwf, 0x1000
0x11000~0x11FFF : composite_ascii, 0x1000
0x12000~0x13FFF : composite_components_0, 0x2000
0x14000~0x15FFF : composite_components_1, 0x2000
0x16000~0x17FFF : composite_components_2, 0x2000
```

Python 빌드의 `_install_composite_resources()`는 다음을 강제한다.

1. ASCII 원본 길이가 `0x1000`인지 확인한다.
2. 한글 원본 길이가 `0x2D00`인지 확인한다.
3. 한글 컴포넌트를 `0x6000`까지 0으로 패딩한다.
4. 패딩 결과를 `0x2000`씩 세 청크로 나눈다.
5. CD 배치표의 세 청크에 각각 넣는다.

`asmbasic.asm`의 `copyFnt`는 확장 RAM bank 0을 연결하고 `0xA300`의 데이터 0x2000바이트를 확장 RAM 주소 0으로 복사하는 기존 전송 루틴이다. 실제 CD 로딩과 세 청크의 공급은 BASIC/CD 데이터 로딩 경로가 담당하며, VWF는 로드가 끝난 bank 0 주소를 읽는다.

## 7. VWF 런타임 동작

### 7.1 문자열 상태

VWF는 다음 상태 주소를 사용한다.

```text
vStrAddr         = 0xB412  ; 현재 문자열 포인터
vStrLen          = 0xB41C  ; 문자열 바이트 길이 규약
vCharCount       = 0xB41D  ; 남은 처리 단위
vScreenPos       = 0xB410  ; 현재 화면 주소
vStartScreenPos  = 0xB414  ; 줄 시작 화면 주소
vLineBreakHeight = 0xB416  ; 줄바꿈 높이
vPrintBuffer     = 16바이트
vPrintBuffer2    = 16바이트
vKanjiBuffer     = 32바이트
```

문자열 길이와 화면 셀 수는 같은 값이 아니다.

- ASCII: 입력 1바이트, 화면 1셀, 8픽셀 전진
- 한글: 입력 2바이트, 화면 2셀, 16픽셀 전진
- 줄바꿈: 화면 주소를 16행 기준으로 다음 줄로 이동

한글 토큰을 읽으면 후행 바이트까지 소비한 뒤 `vGlyphCells=2`로 설정한다. ASCII는 `vGlyphCells=1`로 설정한다. 다음 문자 계산은 이 셀 수를 이용해 `vScreenPos`를 갱신한다.

### 7.2 한글 버퍼 변환

한글 조합 결과는 32바이트, 즉 각 행에 2바이트가 교차하는 16×16 버퍼다. `prepareKoreanBuffers`는 이를 화면 출력용 두 버퍼로 분리한다.

```text
vKanjiBuffer의 각 행 첫 번째 바이트 → vPrintBuffer
vKanjiBuffer의 각 행 두 번째 바이트 → vPrintBuffer2
```

이후 두 버퍼를 같은 화면 행 범위에 연속 출력한다. 따라서 한글 조합 자체는 16×16이고, 화면 메모리에서는 8픽셀 셀 두 개로 표시된다.

### 7.3 실제 출력

`printBuffer16`은 버퍼의 16바이트를 모두 출력한다. 한 행을 출력한 뒤 화면 주소에 `0x50`을 더해 다음 raster 행으로 이동한다.

```text
출력 행 수: 16
다음 화면 행: 현재 주소 + 0x50
ASCII 출력 폭: 1바이트 = 8픽셀
한글 출력 폭: 2바이트 = 16픽셀
```

따라서 본문에서 상하가 잘리는 문제는 글리프 RAW의 조합 여부와 별개로, 호출 경로가 사용하는 화면 시작 주소·16행 출력 범위·줄 간격이 일치하는지 함께 확인해야 한다.

### 7.4 줄바꿈

`_nextLine`은 줄 시작 주소에 `0x0500`을 더한다. 이는 화면 한 행의 주소 간격 `0x50`에 16을 곱한 값이다.

```text
0x50 * 16 = 0x500
```

Python의 `LineLimit`은 픽셀 폭 기준이다. 현재 값은 600이며, 한글은 16, ASCII는 8을 더한다. 이 값은 BASIC 행의 바이트 용량 제한이 아니다. BASIC 문자열 조각은 별도로 `0xF0` 미만인지 검사한다.

## 8. 확장 RAM과 호출 경계

### 8.1 LB52F 호출 게이트

`asmmain.asm`의 `LB52F`는 `LB420`의 공개 진입점에서 호출되는 현재 조합 VWF 게이트다.

현재 소스의 순서는 다음과 같다.

```text
DI
→ 포트 0x31에 0x7B 출력
→ 포트 0xE2에 0x11 출력
→ 포트 0xE3에 0 출력
→ bank 0의 0x0000으로 CALL
→ 포트 0x32 상태를 읽어 독립 접근 상태 복구
→ 포트 0x5F 복구
→ 포트 0xE2 해제
→ 포트 0x31에 0x79 출력
→ EI
→ RET
```

VWF 내부는 이 게이트가 연결한 bank 0에서 실행되며, VWF 자체가 `0xE2`와 `0xE3`를 종료 처리하지 않는다. 호출 게이트가 VWF 반환 후 확장 RAM과 I/O 상태를 복구한다.

### 8.2 렌더러 상태 초기화

`LCA4F`는 BASIC VWF 핸들러가 시작될 때 상태 변수만 초기화한다.

- `LB400` 계열 상태 바이트 초기화
- `vStarted` 초기화
- `vRightMargin` 초기화
- 포트 I/O는 수행하지 않음

확장 RAM 연결과 하드웨어 상태 복구는 `LB52F` 호출 게이트가 담당한다. 이 둘은 같은 역할이 아니다.

### 8.3 직접 출력 경로

`LBF6A`는 BASIC 문자열을 거치지 않고 고정 메시지를 `LB420`으로 전달하는 직접 경로다. 현재 고정 데이터 `LC053`은 조합 VWF가 지원하는 ASCII 문장으로 저장되며, 29바이트 고정 슬롯 안에서 길이 센티널 규약을 유지한다.

따라서 VWF를 분석할 때 일반 `CMD KANJI` 경로뿐 아니라 다음도 함께 검사해야 한다.

- `LB420`의 일반 호출
- `LBF6A → LC053 → LB420` 직접 호출
- 고정 슬롯의 실제 데이터 길이와 센티널
- 직접 호출 후 포인터·I/O 상태 복귀

## 9. Python 컴파일러와 VWF의 바이트 계약

### 9.1 문자 폭

현재 컴파일러의 폭 계산 규칙은 다음과 같다.

```text
한글 토큰 문자: 16
ASCII 0x20~0x7F: 8
내부 따옴표 표식: 8
그 밖의 지원하지 않는 문자: 오류
```

ASCII 폭표는 256칸으로 유지하지만 실제 출력 폭을 갖는 범위는 `0x20~0x7F`다. 폭 계산 결과는 VWF의 화면 전진 폭과 일치해야 한다.

### 9.2 문자열 바이트

컴파일된 BASIC 문자열에서 한글은 2바이트 토큰으로 들어간다. ASCII는 1바이트다. VWF의 `vStrLen`은 화면 폭이 아니라 입력 바이트 소비와 관련된 길이 규약이므로, 한글을 1바이트로 계산하면 후속 토큰과 제어 바이트 위치가 틀어진다.

문자열 조각은 다음을 모두 만족해야 한다.

```text
생성 문자열 조각 바이트 수 < 0xF0
BASIC 행 크기 제한 이내
전체 BASIC 파일 크기 제한 이내
```

### 9.3 따옴표와 줄바꿈

BASIC 문자열 안의 큰따옴표를 raw `0x22`로 삽입하지 않는다. Python 컴파일러는 내부 따옴표 표식을 사용해 BASIC 표현식의 `CHR$(34)` 경로로 변환한다.

백틱은 ASCII `0x60`, 아포스트로피는 ASCII `0x27`로 처리된다. VWF 줄바꿈 바이트인 `0x5C`와 혼동해서는 안 된다.

### 9.4 `< >` 제어 구문

BASIC의 `< >` 비교 구문은 문자열 안에 raw `0x3C 0x3E`를 단순 삽입하지 않는다. 컴파일러는 BASIC 예약어/연산자 토큰으로 직렬화한다.

이 규칙이 깨지면 파서가 다음 바이트를 잘못 해석할 수 있다. 특히 `RST 08H`가 인라인 기대 바이트와 현재 스트림 바이트를 비교하는 지점에서 실패하고, 공통 파서 오류 경로로 들어갈 수 있다. 따라서 다음 검사는 빌드 검증에 포함되어야 한다.

1. `RST 08H`의 기대 바이트와 실제 스트림 바이트가 같은지
2. 문자열·수치·제어 토큰의 소비 길이가 맞는지
3. 파서 현재 위치의 실제 RAM 바이트가 예상 위치와 같은지
4. 파서 오류 경로로 들어가지 않는지
5. 기준 영문 스트림과 한글 스트림의 제어 구조가 의도대로 대응하는지

이 검사는 출력 글리프가 보이는지와 별개의 BASIC 스트림 문법 검사다.

## 10. 빌드 입력과 산출물 검증

현재 Python 빌드의 조합 글리프 준비 단계는 다음을 확인한다.

```text
ASCII 원본: 0x1000 바이트
한글 컴포넌트 원본: 0x2D00 바이트
패딩 후 컴포넌트: 0x6000 바이트
컴포넌트 청크: 0x2000 바이트 × 3
```

정적 검증 항목은 다음과 같다.

- 토큰표 인덱스가 0부터 연속인지
- 문자·Unicode·조합값·토큰 바이트가 서로 일치하는지
- 선두·후행 토큰이 제어 바이트와 충돌하지 않는지
- ASCII RAW와 한글 RAW 길이가 정확한지
- 세 컴포넌트 청크의 크기가 각각 `0x2000`인지
- CD 배치 주소와 크기가 `i_cddata.csv`와 일치하는지
- VWF RAW가 `asm.csv`에서 주소 `0`으로 연결되는지
- `vFontNumber`, `copyFntBank1`, 구형 3종 폰트 선택 경로가 현재 active source에 남지 않았는지
- BASIC 행의 문자열·제어 토큰이 파서 문법과 바이트 단위로 일치하는지
- 실제 에뮬레이터에서 메뉴와 각 스크립트 전환이 진행되는지

정적 검증은 파일 구조·바이트·주소를 확인하고, 에뮬레이터 검증은 실제 CD 로딩·입력 대기·스크립트 전환·화면 출력을 확인한다. 둘은 대체 관계가 아니다.

## 11. 현재 구조의 핵심 요약

```text
ASCII 입력
  → 1바이트
  → 0x1000 + code*16
  → 16행 출력
  → 8픽셀 전진

한글 입력
  → 2바이트 토큰
  → lead/trail 인덱스
  → 초성·중성·종성 조합
  → 32바이트 16×16 버퍼
  → 16바이트 버퍼 2개로 분리
  → 16행 출력
  → 16픽셀 전진
```

현재 구조에서 한글은 1,096개의 완성 음절 RAW를 적재하는 방식이 아니다. 문자열에는 조합 토큰만 들어가고, 실행 중 VWF가 토큰을 초성·중성·종성 인덱스로 분해한 뒤 bank 0의 360개 컴포넌트를 OR 조합한다.

따라서 변경 시 함께 보존해야 하는 계약은 다음 네 가지다.

1. Python 토큰 생성 규칙과 ASM 선두·후행표가 동일할 것
2. 토큰의 2바이트 소비와 화면 2셀 전진을 분리하지 말 것
3. 32바이트 한글 조합 버퍼와 16행 출력 루틴의 주소·행 간격을 보존할 것
4. VWF 반환 뒤 호출 게이트가 확장 RAM·I/O 상태를 복구할 것

이 문서는 위 계약을 현재 소스와 대조하기 위한 기준 문서다. 새 음절, 새 하드코딩 문구, VWF 수정, CD 배치 수정이 생기면 토큰표·컴파일된 BASIC 스트림·ASM 바이트·RAW 크기를 함께 다시 검증해야 한다.
